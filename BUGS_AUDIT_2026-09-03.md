## 3. Бэкенд: механизмы, из-за которых распознанное слово не доходит

### 3.1 Слова interim вытесняются временным окном финала, а не его словами — ПОДТВЕРЖДЕНО
`remote_deepgram_live.py:1640-1657`. Финал 4.91–9.70 «три на или если это» пришёл без слова; interim-слово «субагента» с центром ≈5.7 с попало внутрь окна → удалено и из `_interim_words`, и из orphan-пула. Список `alternatives[0].words` финала (который говорит точно, какие слова он содержит) разбирается только при `diarize=true` (`:1626`). Проверка `is_covered` в сшивке (`:1029-1031`) — тот же тест по центру. Тест `test_deepgram_orphan_pool.py::test_final_confirming_region_clears_orphans` закрепляет эту потерю как желаемое поведение.
Фикс: покрытие — свойство слов, не окон сообщений. Разбирать `words` у каждого `Results`, хранить финалы со списком слов, один общий предикат `covered_by_final_words(word)` в обоих местах.

### 3.2 Orphan-пул чистится любым перекрытием по времени, а не совпадением слова — ПОДТВЕРЖДЕНО
`:1733-1740` — сирота умирает, если хоть одно слово новейшего interim пересекает её отрезок. Скользящая пере-декодировка почти всегда ставит что-то на это место, поэтому пул удерживает слово, только когда новый interim оставил дыру ровно там. Правильный предикат уже написан — `_is_shifted_orphan_duplicate` (`:1047-1060`: совпадение буквенного ядра + большинство перекрытия) — но применяется только при сшивке.

### 3.3 Склейка «фрагментов на стыке» сливает предлоги со следующим словом — ПОДТВЕРЖДЕНО запуском
`merge_seam_fragments`, `:159-228`:

```
'мы живём в' | 'доме на горе' -> ['мы живём вдоме', 'на горе']
'поговорил с' | 'ней вчера'   -> ['поговорил сней', 'вчера']
'иду к' | 'нему домой'        -> ['иду кнему', 'домой']
```

Правило «слить, если ровно одна из соседних лексем без гласной и длина ≤ 4» считает «в/с/к» обрывками. Финалы Deepgram стыкуются с зазором 0.00 с (лог: 0.00–4.91 | 4.91–9.70 | 9.70–12.11), поэтому фильтр 0.05 с не защищает. Теста на реальное безгласное слово нет. Правильное решение — та же словная модель из 3.1: стык склеивать, только если последнее слово `prev` и первое `next` смежны по времени и одно из них не является целым словом в списке провайдера.

### 3.4 `uncoveredSpeechSec` не видит потерю одного слова — ПОДТВЕРЖДЕНО
`:1214-1267` — разность временных отрезков interim и финалов, дыры короче 0.25 с отброшены. Финалы записи 12 с непрерывны → метрика = 0, конверт помечен полным. И это ещё не всё: рендерер поле **не читает** — в парсере `type === "final"` (`main.tsx:389-418`) `uncoveredSpeechSec` отсутствует, поэтому проверка в 10996 и предупреждение в 11080-11087 — мёртвый код.

### 3.5 `UtteranceEnd` от Deepgram выбрасывается — ПОДТВЕРЖДЕНО
`:1578-1579`. При `utterance_end_ms=2000` Deepgram сам сообщает «фраза кончилась, финала может не быть» — ровно то, что `_tail_needs_flush` пытается вывести по байтам.

### 3.6 Зависший `send` роняет чанк, не переподключается и блокирует приёмник на 5 с — ПОДТВЕРЖДЕНО
`:661-708` + `backend/main.py:4215`. `send_pcm` ждётся прямо в цикле приёма кадров рендерера: каждый таймаут = 5 с, за которые ни один кадр не уходит, а `finalize` пользователя стоит в очереди за сотнями бинарных кадров. Лог: 4 подряд в одной записи 2026-09-02 00:40 (20 с простоя), два фатальных случая. `bytes_sent` занижается → `tail_gap` меньше → бюджет finalize занижен. ГИПОТЕЗА с высокой уверенностью: отмена `ws.send` через `wait_for` посреди кадра оставляет соединение `websockets` в неопределённом состоянии — объясняет серии зависаний в одной сессии. Фикс: очередь между приёмником и отдельной задачей-отправителем; зависание детектировать по глубине/возрасту очереди, а не отменой записи; батчить кадры до 50 мс (сейчас ≈375 кадров/с по 85 байт).

### 3.7 Приёмник не запущен, пока идёт connect; recovery-спул пуст при провале connect — ПОДТВЕРЖДЕНО
`backend/main.py:4165` (`await session.connect()`) раньше `:4290` (`receiver()`). Кадры не теряются (backpressure), но `_record_recovery_chunk` вызывается только из `receiver()`: при таймауте connect 12 с (2026-09-02 18:25 — пользователь диктовал 126 с в мёртвый стрим) спул содержит 0 байт и удаляется (`main.py:3909-3912`). Pre-warm/keep-warm нет ни в одном файле. Фикс: запускать приёмник до connect с буфером и записью в спул; далее — открывать сокет по нажатию хоткея с таймером «брошено без аудио».

### 3.8 `text` и `segments` в конверте — два разных текста — ПОДТВЕРЖДЕНО
`:1329` (text — после `merge_seam_fragments`) против `:1000` (segments — сырые).

### 3.9 Логируется каждый пятый interim и только длина — ПОДТВЕРЖДЕНО

## 4. Рендерер: механизмы потери

### 4.1 `lastInterimText` — одноместный регистр, перезаписываемый каждым финалом — ПОДТВЕРЖДЕНО
`main.tsx:8253-8260`; `live-source.ts:181-195`. Композиция «committed + interim + snapshot» выполняется только при чтении (стоп, автосохранение). Слово из interim N, отсутствующее в финале N, доживает только до финала N+1. В записи 12 с snapshot = «три на sunnette или» (19 символов, восстановлено), а interim с «субагента» стоял до первого финала и был перезаписан дважды. Проверено: `mergeInterim(base, "…три субагента на")` при слиянии в момент коммита сохранил бы слово. Фикс: сверять в момент коммита финала и накапливать в durable-поле (`recoveredTailText`), а не в регистре.

### 4.2 Защита от повторов в `mergeInterim` ищет по всему тексту, а не у шва — ПОДТВЕРЖДЕНО
`live-source.ts:127-129`: `baseComparable.includes(interimComparable)` — interim «нужно» отбрасывается целиком, если «нужно» встречалось 30 секунд назад. То же для проверки в 145 и для `redecodedTailStart` (90-111), который может заменить осмысленно повторённую фразу. Это ответ на коммит 876a93a: да, дедуп теперь может съесть настоящий повтор («да, да», переформулировка). Тестов на повтор нет.

### 4.3 AGC включён; микрофон стартует на максимуме усиления — ПОДТВЕРЖДЕНО измерением
`main.tsx:4548-4552`: `echoCancellation:false, noiseSuppression:false, autoGainControl:true`. Все три сегодняшних wav начинаются с пика 0 dBFS (в 100-мс окнах пик 1.00 подряд), RMS −7 дБ (крест-фактор 7 дБ при норме 12–18 — сигнал в лимите), затем уровень сползает на 10–15 дБ за первые 5–10 с и не возвращается. Рендерер к сигналу ничего не применяет (проверено: `pushCapturedFrame`, `downsample`, worklet — без усиления). Это AGC Chromium: перед записью усиление выкручено вверх, первые слова с перегрузом, затем сброс. Абсолютные пороги тишины (`CAPTURE_TAIL_ACTIVITY_RMS = 0.003`, 8721) на хвосте в −28 дБ теряют смысл. Влияние на распознавание — ГИПОТЕЗА; контрольный прогон §1 показал, что потери `multi` от уровня не зависят, так что это отдельный дефект качества сигнала (перегруз первых слов, бессмысленные абсолютные пороги тишины), а не причина потерь. Проверяется A/B с `autoGainControl:false`.

### 4.4 `stopMediaRecorderAndFlush` стоит перед отправкой `finalize` — ПОДТВЕРЖДЕНО
`main.tsx:9821` раньше `9910`. См. 2.4.

### 4.5 ScriptProcessor-фолбэк теряет первые 1.3 с и далее теряет при занятом UI — ПОДТВЕРЖДЕНО
`main.tsx:9444-9466`, `8031-8069`, `fallbackInitDelayMs = 1300`. До срабатывания сторожа ничего не захватывает; затем `createScriptProcessor(4096)` на главном потоке, где `persistLiveDraft` вызывается на каждом `segments` (9152) с полной композицией текста. Узкое окно двойного захвата (9458-9465). На текущей сборке сработал 1 раз (2026-08-31 21:12).

### 4.6 `wsFramesNeverSent` проверяется только для локального провайдера — ПОДТВЕРЖДЕНО
`main.tsx:10703-10708`; путь Deepgram его не читает. Буфер `WS_PENDING_MAX_SAMPLES = 64_000` (4 с) относится к сокету рендерер→локальный бэкенд; при холодном старте бэкенда кадры старше 4 с молча теряются, и на пути Deepgram об этом никто не узнаёт.

### 4.7 ≈310 мс после хоткея не захватывает ничто — ПОДТВЕРЖДЕНО
`getUserMedia: 82 → audioContext: 33 → first-frame: 172`; pre-roll нет, `MediaRecorder` стартует после `getUserMedia`. Первая слогa фразы, начатой на нажатии, отсутствует и в wav, и в стриме. Фикс — тёплый граф захвата с кольцевым буфером в ворклете.

### 4.8 `unionTranscripts`: три реальных режима отказа — ПОДТВЕРЖДЕНО
`transcript-merge.ts:175-218`. (а) `flushGap` при двустороннем расхождении отбрасывает удержанный текст целиком — «sunnette» исчезнет, если конверт на этом месте имеет другое чтение; (б) порог сходства `pairs / min(a,b)` — однословный конверт тривиально проходит и выравнивается по первому совпадению; (в) `UNION_MAX_WORDS = 600` — записи длиннее ≈4 минут возвращаются к «взять более длинный» из коммита до 60a2cc3. Регистр/пунктуация/латиница-кириллица — в порядке.

### 4.9 Слишком короткая запись измеряется от первого кадра — ГИПОТЕЗА
`main.tsx:7931-7935`, `minRecordingMs = 500` от `startAt` (первый кадр, ≈+310 мс) → фактический порог ≈810 мс от нажатия; однословная диктовка («да», «стоп») попадает под сброс.

## 6. Electron-оболочка и вставка

### 6.1 Windows: успех вставки определяется только кодом выхода `cscript`; затем буфер обмена затирается — ПОДТВЕРЖДЕНО
`desktop/main.js:4103-4111`: `if (check.ok)` → `ok:true`, stdout `OK:vbs-paste` не читается; `AppActivate` возвращает boolean, который VBS выбрасывает, у `SendKeys "^v"` режима отказа нет. Далее `_markRecordingPasted` и через 1.5 с `scheduleSmartClipboardRestore` возвращает старый буфер. Для сравнения macOS-ветка (`4302-4309`) требует `out.startsWith("OK:")`. Это самое вероятное объяснение «на Windows ничего не вставилось, а приложение говорит, что вставило». Фикс: требовать `OK:` в stdout, в VBS `If Not WshShell.AppActivate(pid) Then … Quit 2`, и никогда не восстанавливать буфер при `verified === false`.

### 6.2 Windows: целевое окно фактически не активируется — ПОДТВЕРЖДЕНО
`4063-4070`: `AppActivate` добавляется только при `!effectiveTarget.hwnd`, а `getFrontmostAppInfo` на Windows (`3128-3177`) всегда возвращает `hwnd` — обе ветви активации мёртвые. Остаётся `activateWindowsWindowByHwnd` (`3316-3345`): `SetForegroundWindow` из дочернего PowerShell, которому Win32 отказывает (не foreground-процесс), результат отброшен через `Out-Null`. `Ctrl+V` уходит в то, что оказалось спереди — часто в собственное окно Transcriptor.

### 6.3 Windows: цель захватывается компиляцией inline-C# в PowerShell с бюджетом 1200 мс — ПОДТВЕРЖДЕНО
`2188` → `3128-3170`. На macOS быстрый путь `lsappinfo` (~10 мс); на Windows быстрого пути нет, `Add-Type` компилируется при каждом вызове (700–2000 мс холодно, хуже с Defender). При таймауте — пустая цель → `no-target` или «что спереди сейчас». На macOS тот же бюджет один раз превышен даже с `osascript` (1381 мс).

### 6.4 Windows: три компиляции PowerShell на вставку и лестница повторов до ≈30 с — ПОДТВЕРЖДЕНО
`2188`, `3762`, `3796`, `3339` (5 с таймаут), `4103` (5 с), PowerShell-фолбэк только на `attempt === 2` (`4127`).

### 6.5 macOS: восстановление буфера может сработать до того, как цель прочитала pasteboard — ПОДТВЕРЖДЕНО по коду, частота — ГИПОТЕЗА

Фикс: не восстанавливать при `verified === false`, либо ≥4 с, либо до следующего копирования пользователя.

### 6.6 `verified` всегда `false` — верификации нет — ПОДТВЕРЖДЕНО
13 точек возврата с литералом `verified: false`. `OK:menu-paste-primary` означает лишь: у цели есть Edit ▸ Paste, пункт включён, клик отправлен. Фикс: снимать `AXValue`/`AXNumberOfCharacters` фокусного элемента до/после.

### 6.7 Хэндофф транскрипта — опрос `executeJavaScript` каждые 30 мс до 32 с — ПОДТВЕРЖДЕНО
`2499-2572`, `4686-4885`: до ~1000 синхронных вычислений в рендерере ровно тогда, когда он финализирует Deepgram, гонит апскейл и сериализует аудио. `last_transcript.json` пишется после — это копия для хоткея «вставить последнее», не канал. ### 6.8 Может быть вставлен текст до апскейла — ПОДТВЕРЖДЕНО

# Чек-лист проверки на Windows (релиз 1.6.2)

Этот документ — не описание новых фич 1.6.2 (их всего две, обе в рендерере,
см. `CHANGELOG.md`). Это чек-лист для того, что менялось **в Windows-путях
раньше** и ни разу не проверялось на живой Windows-машине — сборка и вставка
через VBS/PowerShell целиком выполняются на macOS в CI и вручную не
запускались на Windows-железе. Каждый пункт — одна проверка и один ожидаемый
результат; где есть точная строка лога — она указана дословно.

Что проверять: соберите и установите билд по разделу 1, затем в реальных
приложениях (Блокнот, Word, браузер, Telegram) наговорите короткую фразу,
остановите запись и посмотрите на `%APPDATA%\transcriptor\main.log` для
каждого пункта.

## 1. Сборка и установка

- [ ] **Сборка запускается командой `npm run dist:win` из `desktop/`.**
      Ожидаемо: скрипт по очереди выполняет `scripts/require-bash.js
      win-x64`, `scripts/prepare-runtime.sh win-x64` (скачивает
      автономный CPython и ffmpeg под win-x64 через кросс-платформенный
      `pip --platform`, без выполнения чужих бинарников на Mac-хосте
      сборки), `unlockDist.js`, `npm run build:frontend`, затем
      `electron-builder --win --x64`. Собирается на macOS — отдельной
      Windows-машины для сборки не требуется.
- [ ] **Версия рантайма, который упаковывается в installer, берётся из
      `desktop/package.json` (`runtime/win-x64` → `extraResources` →
      `to: "runtime"`).** Ожидаемо: `desktop/package.json` и
      `frontend/package.json` показывают `1.6.2` (packaging-drift тест
      `desktop/packaging.test.js` падает, если версии разошлись).
- [ ] **Установщик — NSIS, один клик, без выбора каталога установки.**
      Ожидаемо (см. секцию `nsis` в `desktop/package.json`):
      `oneClick: true`, `perMachine: false` (устанавливается для текущего
      пользователя, без прав администратора), ярлык на рабочем столе и в
      меню «Пуск» с именем `Transcriptor`, установщик сам запускает
      приложение после установки (`runAfterFinish: true`), деинсталлятор
      **не** удаляет данные приложения (`deleteAppDataOnUninstall: false`).
- [ ] **После установки в трее/меню «Пуск» приложение называется
      `Transcriptor`, версия в `О программе` (или в заголовке окна) —
      `1.6.2`.** Ожидаемо: совпадает с `desktop/package.json`.

## 2. Горячие клавиши

- [ ] **Хоткеи по умолчанию на Windows — `Ctrl+Alt+Shift+R` (запись) и
      `Ctrl+Alt+Shift+V` (вставка).** Источник — `platformDefaults.default`
      в `desktop/shortcut-defaults.json` (macOS использует другую пару,
      `Alt+Left` / `Alt+Shift+V` — это ожидаемо, для Windows строка
      `default` профиля). Ожидаемо: обе комбинации срабатывают из любого
      приложения на переднем плане, не только из окна Transcriptor.
- [ ] **Старая пара `F9`/`F10`, если она осталась в конфиге с прошлой
      версии, автоматически превращается в `Ctrl+Alt+Shift+R`/`…+V` при
      первом запуске 1.6.2, а не остаётся как есть.** Это миграция
      `winLinuxFunctionPair` в `desktop/shortcut-migration.js` — на
      Windows/Linux она раньше не была реализована в рендерере (D-015) и
      воспроизводится в `frontend/tests/renderer-main-contract.test.ts`
      только на фикстурах, не на реальном хранилище настроек Windows.
      Ожидаемо: после обновления с версии, где стояли `F9`/`F10`, в
      Settings показаны новые комбинации, а не `F9`/`F10`.
- [ ] **Если пользователь сам назначил свою комбинацию (не `F9`/`F10` и
      не старый дефолт), миграция её не трогает.** Ожидаемо: кастомная
      комбинация остаётся как была после обновления.

## 3. Маркер успешной VBS-вставки (`OK:vbs-paste`)

- [ ] **Вставка через `cscript` (VBS с `SendKeys "^v"`) печатает
      `OK:vbs-paste` последней строкой при успехе.** Раньше `.vbs`-файл
      записывался и читался как UTF-8/ANSI; `cscript //U` на самом деле
      отдаёт вывод в UTF-16LE, и при побайтовом UTF-8-чтении маркер
      разваливался на `O\0K\0:\0v\0…` и не распознавался парсером. Теперь
      декодирование — по флагу `//U` командной строки, явно как
      `utf16le` (`desktop/child-io.js`). Ожидаемо: успешная вставка на
      **любой раскладке и с любым заголовком целевого окна** (включая
      кириллицу, например заголовок вида «Телеграм») определяется как
      успех, а не как молчаливая ошибка.
- [ ] **Сам `.vbs`-скрипт записывается на диск с BOM `0xFF 0xFE` (UTF-16
      LE), а не как обычный текстовый файл.** Ожидаемо: если вставка
      идёт в окно с не-ASCII заголовком, `AppActivate` находит нужное
      окно, а не падает на «кракозябрах» из-за того, что `cscript`
      понял файл в системной кодовой странице (CP-1251 и т.п.) вместо
      UTF-16.

## 4. Отчёт об ошибке `AppActivate` (а не тихое предположение об успехе)

- [ ] **Если `WshShell.AppActivate(...)` не смог активировать целевое
      окно, скрипт печатает `ERR:activate` и завершается с кодом 2,
      *не* нажимая `SendKeys "^v"` вслепую.** Раньше результат
      `AppActivate` не проверялся вовсе, и `SendKeys` мог улететь в
      случайное окно на переднем плане (часто — в само Transcriptor).
      Ожидаемо: сверните/закройте целевое окно между началом записи и
      остановкой — вставка должна сообщить об ошибке активации
      (`reason` содержит `ERR:activate` или ведёт к переходу на
      PowerShell-фолбэк), а не тихо «вставиться» не туда.
- [ ] **После `ERR:activate` ладдер переходит на PowerShell-фолбэк
      (SendKeys без компиляции C#), а не считает попытку успешной.**
      Ожидаемо: итоговый `[paste-auto]` за эту попытку либо в итоге
      успешен через фолбэк, либо честно сообщает о провале — но не
      «успех» на несостоявшейся активации.

## 5. Постоянный PowerShell-помощник переднего окна

- [ ] **Первый вызов определения активного окна после запуска
      приложения — самый медленный: PowerShell-процесс поднимается и
      один раз компилирует P/Invoke-класс через `Add-Type` (может
      занимать ~0.7–2 с, дольше под активным сканированием Defender).**
      Это ожидаемо и не баг: измерьте задержку первого хоткея записи
      после запуска приложения — она заметно больше, чем у второго и
      последующих в той же сессии.
- [ ] **Второй и все следующие вызовы в той же сессии приложения —
      быстрые (десятки мс), потому что используют уже поднятый и
      прогретый PowerShell-процесс, а не поднимают новый.** Ожидаемо:
      нажмите хоткей записи несколько раз подряд — только первый раз
      заметна задержка.
- [ ] **Если PowerShell-помощник упал или завис, следующий вызов
      перезапускает его самостоятельно (без перезапуска всего
      приложения).** Ожидаемо: снятие процесса `powershell.exe`,
      обслуживающего помощника, через Диспетчер задач не «ломает»
      хоткеи навсегда — следующая попытка снова поднимает помощника
      (с новой задержкой первого вызова).
- [ ] **След `front_before` в логе фиксируется на каждом определении
      переднего окна — при нажатии хоткея записи, перед вставкой и
      после остановки.** Ищите в `main.log` строки вида
      `"stage":"front_before"` (внутри `[trace]`-записей с разными
      `scope`: `toggle_hotkey`, `paste`, `post_stop`) — там же поле
      `ms`, которое и показывает разницу между холодным первым вызовом
      и прогретыми следующими.

## 6. Бюджет повторов и таймаутов на Windows

Источник — `PASTE_BUDGET.win32` в `desktop/paste-capability.js`.

- [ ] **Максимум попыток вставки — 2 (не 3, как на macOS/Linux).**
      Ожидаемо: при недоступной цели вставки видно не больше двух
      циклов «VBS → PowerShell-фолбэк» в логе на одну попытку остановки
      записи.
- [ ] **Задержки перед попытками — 30 мс и 60 мс.** Пауза перед второй
      попыткой заметно короче секунды.
- [ ] **Таймаут на сам `cscript` (VBS) — 3500 мс, на PowerShell-фолбэк —
      3000 мс.** Это учитывает, что запуск `cscript` может занимать
      1–3 с под активным сканированием Defender. Ожидаемо: даже на
      медленной машине с антивирусом одна попытка вставки не «зависает»
      дольше суммы этих двух таймаутов.
- [ ] **Активация цели (поиск переднего окна через помощника) имеет
      таймаут 2500 мс и до 3 попыток ладдера активации (по hwnd, по
      pid, по имени процесса) на одну попытку вставки.** Ожидаемо: даже
      если один способ определения окна не сработал, вставка не «висит»
      неограниченно — переходит к следующему способу в пределах общего
      бюджета.
- [ ] **Проверки (verification) на Windows нет вообще
      (`verificationAllowanceMs: 0`) — в отличие от macOS, где после
      вставки читается `AXValue` поля.** Ожидаемо: Windows-вставка
      никогда не помечается как `verified=1` в логе — это норма для
      платформы, не баг (см. пункт 7).
- [ ] **Автоотправка Enter после вставки (если включена) имеет таймаут
      2000 мс и паузу 380 мс перед отправкой (даёт целевому приложению
      время принять вставленный текст).** Ожидаемо: если автоотправка
      включена, Enter уходит не мгновенно после вставки, а с короткой,
      но заметной паузой.

## 7. Восстановление буфера обмена никогда не происходит при неудаче
   (и на Windows — фактически никогда)

- [ ] **Если вставка не подтверждена (`verified !== true`), исходное
      содержимое буфера обмена НЕ восстанавливается — расшифрованный
      текст остаётся в буфере.** Это касается любой платформы: провал
      вставки не должен ещё и стирать единственную копию текста, которая
      у пользователя осталась (в буфере).
- [ ] **На Windows подтверждения (`verified`) не существует в принципе
      — оно всегда `false`, даже при успешной вставке.** Поэтому после
      **любой** Windows-вставки, успешной или нет, буфер обмена
      сохраняет расшифрованный текст, а не возвращает то, что было в
      буфере до записи. Ожидаемо: скопируйте что-нибудь в буфер, начните
      запись, продиктуйте фразу, остановите — после вставки в буфере
      должен быть транскрипт, а не то, что было скопировано раньше. Это
      ожидаемое поведение платформы, не регрессия.
- [ ] **Лог подтверждает это явной строкой.** Ищите
      `[paste:clipboardRestore:vbs]` или
      `[paste:clipboardRestore:pwsh_fallback]` со текстом `paste not
      verified; leaving transcript on the clipboard instead of
      restoring`.

## 8. Какие строки лога смотреть, чтобы подтвердить каждый пункт

Файл: `%APPDATA%\transcriptor\main.log` (аналог
`~/Library/Application Support/transcriptor/main.log` на macOS).

- [ ] **`[paste-auto] app="…" pid=… method=vbs_paste|pwsh_fallback
      verified=0 reason="…" len=…`** — одна строка на завершённую
      попытку вставки: какое приложение было целью, какой метод
      сработал, подтверждение (всегда `0` на Windows, см. пункт 7),
      причина и длина текста.
- [ ] **`[trace] {"id":"paste-…","scope":"paste","stage":"…", …}`** —
      пошаговый след одной вставки: `front_before` (определение
      переднего окна и его задержка), `target_activation_skipped` /
      `target_activation_failed` (активировалась ли цель до отправки
      клавиш), `clipboard_write_ok`, `paste_verification_policy`,
      `method_begin` / `method_result` (какой метод — VBS или
      PowerShell — и с каким кодом возврата).
- [ ] **`[trace] {"id":"post_stop-…","scope":"post_stop", …}`** — вся
      цепочка после остановки записи: `ipc_provisional` /
      `ipc_final` / `transcript_ready` (когда рендерер отдал текст) и
      `target_current_focus` / `paste_result` (что происходило с
      вставкой). По `elapsedMs` в `paste_result` видно, сколько от
      остановки записи до готовой вставки в реальности заняло время —
      сравните с бюджетом из раздела 6.
